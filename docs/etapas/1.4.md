# Etapa 1.4: Terraform y estado remoto

## Objetivo

Gestionar la infraestructura del laboratorio con Terraform desde el primer recurso, con el estado guardado en un bucket privado y versionado, y un inventario que muestre qué existe en el proyecto.

**Terminado cuando:** el plan se puede explicar antes de aplicarlo y un plan posterior no muestra cambios.

**Estado:** terminada (verificada en GCP el 2026-11-24). Cambio respecto del plan: el bloque B2 pasó directo a estado remoto (en el plan, el estado remoto era de la 4.5) y no se hizo el ciclo `destroy` → `apply` del bucket; el `destroy` del entorno se hace en el B6.

## Pasos hechos

1. Región decidida: `us-central1`.
2. `infra/bootstrap/main.tf`: bucket `python-gcp-ai-lab-tfstate`.
   - Privado: acceso uniforme y `public_access_prevention = "enforced"`.
   - Versionado, con una regla que borra las versiones viejas más allá de las últimas 5.
   - `force_destroy = true`, para poder retirarlo al final junto con sus versiones.
   - Su propio estado queda local y no se versiona (`*.tfstate` está en `.gitignore`).
3. `infra/versions.tf`: backend `gcs` en ese bucket (prefijo `infra`), proveedores `google ~> 8.12` y `random ~> 3.9` (últimas versiones en el registro de Terraform: 8.12.0 y 3.9.1), y `default_labels = { lab = "gcp-ai" }`.
4. Los archivos de `infra/` son planos, sin módulos: `apis.tf`, `registry.tf`, `iam.tf`, `sql.tf`, `secrets.tf`, `run.tf`, `variables.tf` y `outputs.tf`.
5. `scripts/inventario.sh`: lista los recursos que pueden cobrar. Consulta una vez las APIs habilitadas y salta las secciones cuya API está apagada.

## Comandos usados

| Comando | Para qué |
|---|---|
| `terraform -chdir=infra/bootstrap init` | Descargar el proveedor y preparar el directorio (estado local). |
| `terraform fmt -recursive` | Formatear todos los `.tf` con el estilo estándar. |
| `terraform validate` | Revisar la sintaxis y las referencias sin tocar la nube. |
| `terraform plan -out=archivo.tfplan` | Calcular los cambios y guardarlos, para aplicar exactamente lo revisado. |
| `terraform apply archivo.tfplan` | Aplicar el plan guardado. |
| `terraform -chdir=infra init` | Configurar el backend GCS (el estado pasa a vivir en el bucket). |
| `terraform apply -target=...` | Aplicar solo algunos recursos (APIs, repositorio y cuenta de servicio) antes de subir la imagen. |
| `terraform output` | Ver los valores de salida (URL del servicio, registro, job, instancia). |
| `bash scripts/inventario.sh` | Listar los recursos del proyecto (desde Git Bash). |

## Problemas y solución

| Problema | Solución |
|---|---|
| `terraform validate` fallaba con cualquier proveedor (incluso `random`): `transport: authentication handshake failed: tls: failed to verify certificate: x509: certificate signed by unknown authority`. No era la conexión a Google, sino la conexión local (`127.0.0.1`) entre `terraform.exe` y el proceso del proveedor, que Terraform cifra con certificados que genera en cada ejecución. Pasaba igual sin sandbox, desde PowerShell y con otro rango de puertos. Con el Escudo Web de Avast en pausa seguía fallando; con **todos** los escudos de Avast desactivados, funcionó. | Causa: Avast. Se desactivaron los escudos durante la ventana de los `apply`. Solución estable propuesta: excepciones de Avast para `terraform.exe` y los binarios de los proveedores (pendiente de prueba por Ramiro). |
| El repositorio de Artifact Registry tiene que existir antes de subir la imagen, y el servicio de Cloud Run necesita la imagen para crearse. | `apply -target` de las APIs, el repositorio y la cuenta de servicio; después, push de la imagen y `apply` completo. |
