# Etapa 1.3: Docker

## Objetivo

Empaquetar la API en una imagen Docker multi-etapa con `uv`: usuario no root, `.dockerignore`, puerto configurable.

**Terminado cuando:** `/health` y `/quotes` responden dentro del contenedor.

**Estado:** terminada en local. La imagen se construye y `/health` y `/quotes` responden dentro del contenedor (levantado con compose junto a la base, ver la 2.1).

## Pasos hechos

1. `Dockerfile` multi-etapa, siguiendo el patrón de la guía de Docker de uv (verificado en `docs.astral.sh/uv/guides/integration/docker/` y `astral-sh/uv-docker-example`):
   - **Builder:** `python:3.13-slim` con el binario de uv copiado desde `ghcr.io/astral-sh/uv:0.13.7`. Variables `UV_COMPILE_BYTECODE=1`, `UV_LINK_MODE=copy` y `UV_PYTHON_DOWNLOADS=0`. `uv sync --locked --no-dev` en dos capas: primero las dependencias, con montaje de caché, y después el código.
   - **Imagen final:** `python:3.13-slim`, la misma base, porque la ruta del Python del entorno virtual tiene que coincidir. No incluye uv ni herramientas de desarrollo.
   - **Usuario no root** `app` (uid 999).
   - **Arranque:** `CMD` en forma de shell para expandir `${PORT}` (por defecto 8080, como espera Cloud Run); `exec` deja a uvicorn como PID 1.
2. `.dockerignore`: excluye `.git`, `.venv`, `.env`, `privado/`, `tests/`, `docs/`, las cachés y el estado de Terraform.

## Comandos usados

| Comando | Para qué |
|---|---|
| `docker run --rm curlimages/curl -svI https://files.pythonhosted.org` | Ver qué certificado (emisor) recibe un contenedor al conectarse a PyPI. |
| `docker compose up -d --build --wait` | Construir la imagen de la API y levantar el stack en segundo plano. |
| `docker compose exec -T api id` | Ver con qué usuario corre el proceso dentro del contenedor. |
| `docker images` | Ver las imágenes locales y su tamaño. |

## Resultado observado

- Primer intento: `uv sync` falló con `invalid peer certificate: UnknownIssuer` (ver Problemas).
- Con el Escudo Web de Avast en pausa, la imagen se construye sin cambios en el Dockerfile.
- Al arrancar, el contenedor corre `alembic upgrade head` y después uvicorn en el puerto 8080; en el host queda publicado en el 8000.

## Problemas y solución

| Problema | Solución |
|---|---|
| `uv sync` dentro del build fallaba con `UnknownIssuer`. Causa: el **Escudo Web de Avast** intercepta el HTTPS de los contenedores. El tráfico de Docker Desktop sale por su proxy interno (`http.docker.internal:3128`) a través de Windows, y Avast lo vuelve a firmar con su propia raíz (`Avast Web/Mail Shield Root`). Windows confía en esa raíz, por eso `uv` funciona en el host, pero el contenedor no. No había proxy ni VPN configurados. | Se pausa el Escudo Web de Avast solo durante los builds que descargan dependencias, es decir, cuando cambia `uv.lock`; si no cambia, la capa de dependencias sale de la caché. No afecta a CI ni a Cloud Run: allí no hay Avast y el Dockerfile no tiene nada específico de esta máquina (ni `--system-certs` ni verificación TLS desactivada). Alternativa descartada por ahora: pasar el certificado como secreto opcional de BuildKit. |
| El puerto 8080 del host está ocupado por otro proceso. | En compose la API se publica en el puerto 8000 del host; dentro del contenedor sigue en 8080. |
